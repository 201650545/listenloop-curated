# 17 · 产品路线图与版本规划（定稿）

> 定位：ListenLoop 以 APP 为载体，**AI 生成各种交互设计**，提升体验与学习效率，实现有效学习。
> 本稿 = 草案（Agent 起草）+ GPT 镜像站评审（Thinking•Extended，2026-09-29）修订合并。
> 评审全文：`_reply_turn4_roadmap.md`。关系文档：08 / 09 / 15 / 16 号。

## 〇、产品宪法（新增，GPT 评审 ⑤）

> **AI 生成的是受约束的 InteractionSpec，不生成任意 App UI，不绕过 governor/evaluator，不改变核心播放器控制权。**

没有这条，「AI 生成各种交互设计」会被侵蚀成「LLM 返回 JSON、客户端乱渲染」，五层架构、08 号红线、15 号 bounded primitives 全部失守。

## 一、长远目标（12 个月）：听力驱动的语言习得系统

三阶段 AI 角色（15 号不变）：**A 反馈者 → B 设计者 → C 课程架构师**。

Phase C 启动 gate（GPT 评审 ④ 新增）：**只有 LearnerModel 能稳定区分「语言不会」与「知识不会」之后启动**。否则用户答不出「自然选择」，系统不知道该教英语还是教生物。

## 二、核心修正（GPT 评审两大判断）

### 判断 1：W4 验证目标倒置（已采纳）
- ❌ 原稿：W4 验证「AI 能组合题型」
- ✅ 定稿：W4 验证「**AI 能在受限协议内生成可执行、可验证、可降级的 interaction spec**」
- 分界线：不要证明「AI 很会出题」，要证明「APP 已拥有一个 AI 可以安全编排的学习交互运行时」。

### 判断 2：填空/排序/选择不是顶层 primitives（已采纳）
- 它们是 **Response components**（用户怎么输入），不是 Learning Runtime 的顶层 primitive（学习任务如何运行）。
- 顶层最小模型：**Stimulus → Response → Evaluator → Feedback → Transition**
  - Stimulus: meaningCue / originalAudio / sentenceText / tokenSequence
  - Response: freeText / choice / ordering / cloze
  - Evaluator: exact / tokenDiff / ordering / aiSemantic
  - Feedback: correctness / diff / hint / explanation / reference
  - **Transition: retry / advance / relisten / finish**（「错了以后去哪儿」本身就是学习设计——16 号刚证明这一点）
- **Evaluator 原则**：能 deterministic 的一定 deterministic（排序/选择/cloze 本地判）；只有语义等价类才调 governor。这同时满足 08 号降级红线：AI 挂了，Runtime 仍有大量可执行交互。

## 三、中期路线（4 周，修订版）

| 版本 | 交付 | 真正验证什么 |
|---|---|---|
| **v0.9.1**（今晚）| 双出口 + 入口优化 + **MR 一次 modified output** + AI 文本清洗 | 听写完成流第一次真正闭环：诊断能驱动下一动作 |
| v0.9.2 / W2 | Parsing Challenge α + **AttemptResult 结构化** | timed processing + 第二种 interaction |
| v0.9.3 / W3 | Micro Grammar α（**首批 3 个可可靠识别的错误模式**，不叫 top3）+ **Interaction Contract v0**（三种训练的公共协议） | 第三种 interaction + 从真实重复中抽 primitive |
| v0.9.4 / W4 | **InteractionSpec Runtime Spike**：AI 不生成 UI/code，只生成 schema-valid spec；通用 renderer 执行 ≥3 种 interaction graph 不加专用 Screen；非法 primitive/transition 必须拒绝并降级固定模板 | AI 能否安全编排已有 primitives |
| **V1.0** | 三训练正式化 + evidence routing + 留痕 + fallback + E2E | Learning Runtime Phase A |
| V1.1 Preview | AI 根据 learner evidence 动态选 spec/graph | **Phase B 真正开始** |

**W4 四条成功标准**：① AI 只输出 schema-valid InteractionSpec；② 通用 renderer 执行 ≥3 种 graph 零新增 Screen；③ 非法 spec 拒绝并降级；④ 同一 DictationEvidence 经不同合法 spec 产生统一 AttemptResult。

## 四、V1.0 gate（GPT 评审 ② 扩为四条）

1. **evidence-driven routing**：三种训练都从明确 evidence/reason 进入
2. **structured attempt/result**：全链路结构化留痕
3. **governor/fallback**：全部走 governor 且可降级
4. **E2E**：真机端到端复验通过

**V1.0 scope 冻结**：Meaning Recall + Parsing Challenge + Micro Grammar（Chunk Composer 移入 post-V1.0 backlog）。

## 五、v0.9.1 四件套（优先顺序，GPT 修订）

1. **双出口完成流**：ProductionTarget（去意思回忆）+ ListenRetryTarget（回原声重听）
2. **入口位置**：diff 结果区末尾、主导航之前
3. **MR modified output（新增，优先于 Markdown 清洗）**：
   - AI 返回 correct + target repaired → 直接下一句
   - 否则反馈卡显示「意思基本表达到了 ✓ / 这次再注意：xxx」+ **[再说一次]**（primary，仅 1 次 guided retry）+ [看参考表达]（secondary）+ [下一句]（tertiary）
   - 第二次提交后无论结果允许下一句（不无限纠错）
   - 无 AI 静态兜底：「AI 反馈暂不可用，下面是原句供对照」，不要求 repair
4. **AI 文本轻量清洗**（保留，降级为第 4 位）

**Error 153 处置**：不挤占 v0.9.1 四件套（已单独修复并装包）。gate 原则：用户遇到时要知道下一步——做一个「视频暂时加载失败 [重新加载]」的小恢复 UI，不把 Error 153 当主文案。

## 六、连续演进逻辑（GPT 总结，采纳为路线图主轴）

> v0.9.1 证明「诊断能驱动下一动作」→ W2/W3 证明「不同学习动作存在共同协议」→ W4 证明「AI 能在这个协议里设计交互」→ V1.0 把协议和数据正式化 → V1.1 才让 AI 真正开始动态编排。

**APP 提供可靠的交互运行时，AI 根据学习证据设计下一段学习体验。**

## 七、不做清单（沿用 + 新增）

- ❌ TTS / 语音合成（15 号）
- ❌ 完整 Markdown renderer（轻量清洗即可）
- ❌ Chunk Composer（post-V1.0）
- ❌ 推翻五层架构
- ❌ AI 生成任意 UI / 绕过 evaluator（产品宪法）
- ❌ 「top3 错误模式」表述（数据结论 vs 产品决策要分清）
